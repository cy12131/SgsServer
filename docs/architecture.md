# 服务端架构说明（M0）

## 独立服务端

客户端负责交互与展示，服务端负责可信状态和规则执行。独立部署能使生命周期、故障边界和测试范围更清楚，也让 Linux 服务端与 Windows Qt/QML 客户端分别演进。项目只参考 freekill-asio 的模块分工思想，不依赖其安装、源码实现、协议或扩展包。

## 当前入口

`main` 只创建 `Application` 并返回其退出码。`Application` 是进程级生命周期入口：M0 仅输出名称、版本和启动成功信息；未来负责按顺序装配并关闭已经获准实现的服务。输出流由调用方持有，`Application` 只借用它，因此所有权和测试替换方式是明确的。

启动流程为：

1. 操作系统进入 `main`。
2. `main` 以标准输出构造 `Application`。
3. `Application::run()` 输出程序标识和成功信息。
4. `run()` 返回 0，`main` 将退出码交还操作系统。

## 未来模块的预期边界

以下只是职责边界，不代表 M0 已创建或实现对应模块：

- **Network**：监听、连接和字节收发；不解释游戏规则。
- **Session**：表示一个已建立的客户端会话，管理连接级状态；不拥有整局游戏。
- **Room**：组织参与者、席位和房间生命周期，协调一局游戏的创建与结束。
- **Game**：持有并推进服务端权威的对局状态，通过规则判断接受或拒绝操作。
- **Lua**：承载经约定的规则脚本执行能力，不直接管理 Socket 或客户端界面。

模块间的数据契约与通信协议必须由总体架构负责人统一确定，本阶段不作任何预设。

## 服务端权威状态

客户端提交意图，服务端验证并推进状态；客户端显示服务端确认后的结果。随机结果、合法性判定和对局状态应以服务端为准，不能信任客户端自行声明的最终状态。具体消息格式不属于 M0。

## M0 明确未实现

当前没有网络监听或工作线程，没有 HTTP、WebSocket 或自定义 TCP，没有协议、会话、房间、认证、数据库、Lua、卡牌与技能规则、扩展包同步、资源管理、版本兼容校验，也没有动态模块或插件系统。
